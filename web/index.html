How these figures are calculated

Each calendar square counts distinct confirmed transactions involving Ironwood, including transfers across pools. Miner coinbase transactions are excluded. One transaction can add multiple leaves to the tree because each Ironwood action adds a note commitment. The tree also includes actions in miner coinbase transactions. Dates and hours use the block timestamp in UTC. The brightest squares mark the upper quarter of active days in the displayed range. Log scale compresses hourly bar heights using log(1 + count) so smaller values remain visible beside spikes. Tooltips and selected hour counts always show the original transaction totals.

Pool flows use the net Ironwood value of each decoded transaction. Daily covers the selected UTC date. All time covers indexed history. Inflows and outflows have separate totals and medians. The historical decoding status shows how much history has been checked. Fees paid from Ironwood contribute to the transaction’s net pool change, including when the transaction uses only Ironwood. The cross-pool count covers transactions that touch another pool and change Ironwood’s public balance. Amounts paid between shielded users remain private.

Ironwood TPS counts distinct confirmed transactions involving the Ironwood pool, including transfers across pools and excluding miner coinbase transactions. It measures pool activity, not network-wide Zcash TPS or maximum capacity. Daily uses the selected UTC calendar date; All time uses all indexed history. The average divides the transaction count by the seconds in complete indexed hours in that period. Peak hour is the busiest complete hour’s count divided by 3,600. The current partial hour and the partial activation day are excluded. Missing history shows no estimate. All time switches flows and TPS together and restores the busiest-weekday summary.

Weekday rankings compare median transaction counts per complete day in the selected time zone, using available history since Ironwood’s launch (up to one year). Select any weekday to see the hour with the highest median transaction count across its complete indexed days. Tied peak hours use the earliest hour; a peak is unavailable when every hour has a zero median or no complete days are indexed. The average wait for first confirmation uses the time between seeing a pending transaction and indexing its block. The first-to-tenth interval measures how long nine more blocks take after that first block. Both timing figures cover the last seven days. The last complete hour is compared with the same UTC hour on up to 28 preceding days. Shielded block usage measures the share of the NU7 shared action budget consumed by all shielded pools.
